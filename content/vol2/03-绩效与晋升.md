# 绩效与晋升：评审材料怎么写、谁来背书

## 1. 三十秒自检

- [ ] 你觉得"活干得好自然会被看到"
- [ ] 你的晋升材料写着"负责 XX 模块的开发与维护"
- [ ] 你没有在评审前找任何人聊过
- [ ] 你不知道评审会上谁有发言权
- [ ] 你上一次被打低分之后，不知道具体原因

打勾 ≥2 个，往下读。**第一条是最贵的一个错觉。**

## 2. 结论先行

**绩效与晋升评的不是"你做了多少"，是"有多少人能证明你做了什么、以及它的价值"。**

这是很多人不愿意接受的现实，但它是真的：在评审会上，**证据的权重远大于事实**。
你做了十件有价值但无人知晓的事，不如一件被三个人提到的事。

评审通常看四件事，按权重排：

| 维度 | 评审真正在看什么 |
|---|---|
| **产出** | 有没有可量化的结果（不是"做了"，是"从 X 到 Y"） |
| **影响力** | 影响范围是否超出你自己的任务（跨团队、沉淀方法、帮到别人） |
| **协作** | 有没有人愿意说你的好话（这是最容易被忽视但极其关键的一项） |
| **难度/复杂度** | 你做的事有多难——评审会追问细节，答不上来就露馅 |

**最关键的一点：晋升是"提前很久就在准备"的事，不是"材料写出来"的事。**
如果你在评审前一个月才开始准备，你已经晚了至少半年。

## 3. 现在就做

| 时间窗 | 动作 |
|---|---|
| **今天** | 打开你的上一份绩效自评，检查有没有任何一个"从 X 到 Y"的数字。**没有就要重写** |
| **今天** | 列出你今年做的三件事，为每件事找一个"受影响的人"——这个人就是你的潜在背书者 |
| **本周** | 找一个已经晋升过的同级同事聊一次，问他当时是怎么准备的（这是最有效的信息来源） |
| **本周** | 向你的直属上级明确表达："我希望下一次评审能过"，并问清楚他觉得你还差什么 |
| **每月** | 维护一份"成果流水"文档（见第 4 段模板），**不要等到年底才回忆** |
| **评审前 3 个月** | 开始找背书人铺垫（不是拉票，是让人知道你在做什么） |

## 4. 可直接抄的话术 / 模板

### 成果流水模板（每月花 10 分钟维护，年底直接变成材料）

```markdown
## 2026-Q3 成果记录

### 1. XX 系统性能优化
- 背景：P99 延迟 XX ms，业务反馈慢
- 我做了什么：定位到 XX 瓶颈，改用 XX 方案
- 结果：P99 从 XX ms 降到 XX ms（-XX%），机器数从 X 台减到 X 台
- 影响范围：支撑 XX 业务线，日请求量 XX
- 可以作证的人：@XX（合作方）@XX（使用方）

### 2. XX 项目
（同上格式）
```

要点：**每一行都要有数字、有影响范围、有可以作证的人。** 这三点决定了评审能不能"验证"，而不只是"相信"。

---

**场景一：向直属上级明确表达晋升意愿（很多人从来不开这个口）**

> 「我想聊一下晋升的事。我的目标是下一次评审能过。
> 你觉得以我现在的情况，还差在哪些地方？我想提前准备。」

要点：**这段对话的价值在于把标准问出来。** 多数上级在被明确问到时会给出真实的差距说明——这东西你自己猜一年都猜不出来。

**场景二：请他人为你的工作做证明（不拉票的方式）**

> 「上次那个 XX 的方案你来评审了，如果后面有人问起，方便帮我客观说一下当时的情况吗？
> 我准备晋升材料，需要有能验证的人。」

要点：**直接、坦诚、不夸张。** 只请真正了解你工作的人，并且提醒他们"客观说"——过度美化反而降低可信度。

**场景三：被打低分之后的复盘沟通（非常重要）**

> 「关于这次的绩效结果，我想了解一下具体是哪些地方没达到预期。
> 我想知道明确的标准，这样下个周期我能有针对性地改进。
> 如果可能，能不能给我一两个具体的例子？」

要点：**不要争辩分数，只问具体行为。** 争辩会让对方防御；问"具体例子"会让对方必须给出可操作的信息。

**场景四：材料里的项目描述怎么写（对比）**

```
❌ 差：
"负责订单系统的开发与维护，保障了系统稳定运行。"

✅ 好：
"主导订单系统重构：原系统在大促期间 P99 达 2.3s 且存在超卖风险；
主持重新设计库存扣减链路（引入 XX 机制），上线后 P99 降至 180ms，
大促零超卖事故；方案被 XX 团队复用。"
```

差别在于：**前者在描述职责，后者在描述问题、动作、结果和影响半径。**

## 5. 五个常见错误

1. **以为"活干得好自然会被看到"**
   → 后果：这是最贵的一个错觉。评审会上没有人会替你翻你的 commit 记录
   → 正确做法：**每月一次轻量同步 + 维护成果流水**。可见性是可以系统性建设的

2. **材料里只有职责，没有结果**
   → 后果："负责 XX"这种描述在评审里几乎不得分，因为它没有信息量
   → 正确做法：**每一条都用"问题 → 动作 → 结果 → 影响"的结构重写**

3. **临时抱佛脚找背书人**
   → 后果：评审前一周才联系别人，对方既不了解你的工作，也会觉得突兀
   → 正确做法：**提前 3 个月开始铺垫**。铺垫的方式不是请吃饭，是让对方真正参与过你的工作

4. **只向上管理，忽视同级与合作方**
   → 后果：评审时的 360 反馈或跨团队评价很难看
   → 正确做法：**影响力半径要覆盖同级和合作方**。他们才是日常真正看到你工作的人

5. **被打低分后立刻消极或摆烂**
   → 后果：最坏的一种反应。低分之后的第一个季度表现，决定了你下一次评审的起点
   → 正确做法：**立刻做一次复盘沟通，拿到具体改进项，然后在下个周期把它们做出来**。这是唯一有效的反击

## 6. 真实案例（脱敏）

**背景**：某公司两位同期入职、能力相近的工程师申请同一批晋升。

**A（失败）**：材料写了 5 页，详细描述了他负责的模块和各种技术细节。他觉得"我把事情都说清楚了"。评审会上没人提问，因为没人熟悉他的业务。结果未通过。

**B（成功）**：材料只有 2 页，每件事都是"问题 → 动作 → 结果 → 影响"，并且每件事都标注了 1~2 个可以作证的人的名字。评审会上，其中两个人主动发言确认了她的工作。

**关键差别**：不是谁做得更好，而是**谁的成果可以被验证**。A 的材料需要评委"相信他"，B 的材料允许评委"去核实"。

**A 后来的做法**：他花了三个月做两件事——把负责的系统文档化并做了一次跨团队分享（让更多人知道），然后主动承接了一个跨团队的难题。**第二次评审通过了。** 他说：「我以前觉得准备材料是包装，后来明白准备材料是让证据提前存在。」
